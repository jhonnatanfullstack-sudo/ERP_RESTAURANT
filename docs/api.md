# API

## Formato de respuesta

Todas las respuestas de la API siguen un formato consistente (sección 7 de `CLAUDE.md`):

**Éxito:**

```json
{ "success": true, "message": "OK", "data": {} }
```

**Error:**

```json
{ "success": false, "message": "...", "details": [] }
```

Helpers en `src/utils/api-response.ts`: `sendSuccess(res, data, message?, statusCode?)` y `sendError(res, statusCode, message, details?)`. Usar siempre estos helpers en los controladores, no construir la respuesta a mano.

## Manejo de errores

- `src/utils/http-error.ts`: clase `HttpError(statusCode, message, details?)` para errores de negocio/validación conocidos. Lanzarla desde services/controllers; el middleware de errores la traduce automáticamente al formato de la API.
- `src/middlewares/error-handler.middleware.ts`: middleware centralizado (último en la cadena). Los errores no controlados (`Error` genérico) devuelven 500 con mensaje genérico en producción, y el mensaje real solo en `NODE_ENV=development`. Nunca se expone el stack trace al cliente.
- `src/middlewares/not-found.middleware.ts`: responde 404 con el formato estándar para rutas no registradas.

## Seguridad aplicada (FASE 3)

- **Helmet**: cabeceras de seguridad por defecto (`X-Content-Type-Options`, `X-Frame-Options`, `Strict-Transport-Security`, etc.).
- **CORS**: origen restringido a `CORS_ORIGIN` (env), con credenciales habilitadas (necesario para el futuro flujo de refresh token).
- **Rate limiting**: 300 solicitudes / 15 min por IP, aplicado globalmente; `/api/auth/login` tiene su propio límite más estricto (10/15min). Los endpoints públicos (carta, futuros) llevarán un límite propio cuando se implementen (FASE 8-9).
- **Body parser**: `express.json()` con límite de 1MB.
- **Validación**: `zod` en `src/middlewares/validate.middleware.ts` (`validateBody`, `validateIdParam`). Todo endpoint que recibe body o `:id` valida antes de llegar al controller.
- **Autenticación/autorización**: `requireAuth` + `requirePermission(codigo)` (`src/middlewares/auth.middleware.ts`). Ver `autenticacion.md` y `roles-y-permisos.md`.

### Talonarios (series de comprobantes)

Un **talonario** es una serie SUNAT autorizada (`B001`, `F001`, …) con su correlativo vigente y el rango que puede recorrer. Reemplaza la serie fija por tipo de comprobante que traía `venta.service.ts` y permite que dos cajas emitan en paralelo sin pisarse el número.

- **Campos** (`talonarios`): `empresa`, `tipoComprobante`, `almacen` (punto de emisión), `serie` (4 caracteres), `numeroInicio`/`numeroFin` (rango autorizado), `numeroActual` (**último número emitido**, 0 si no emitió nada), `activo`.
- **Siguiente número**: `max(numeroActual + 1, numeroInicio, últimoEmitidoEnVentas + 1)`. El tercer término cubre las ventas anteriores a este módulo (serie fija `B001`/`F001`): un talonario creado después continúa tras ellas en vez de chocar contra el índice único de `ventas (tipo_comprobante, serie, numero)`. La API lo devuelve ya calculado en `siguienteNumero`, `siguienteNumeroFormateado` (`B001-00000001`, 8 dígitos), `numerosDisponibles` y `agotado`.
- **Serie**: única por empresa (índice `IDX_un_talonario_por_empresa_serie`) y debe empezar con la letra que SUNAT exige para su comprobante — `F` factura, `B` boleta (`LETRA_SERIE_POR_COMPROBANTE` en `catalogos/codigos-sunat.ts`). Solo puede cambiarse mientras el talonario no haya emitido nada (409 si ya emitió).
- **Asignación a usuarios** (`talonario_usuarios`): `PUT /api/talonarios/:id/usuarios` con `{ usuarioIds: [] }` **reemplaza** el conjunto completo, igual que los permisos de un rol. Solo los usuarios asignados pueden emitir con esa serie.
- **Eliminar**: `DELETE` solo funciona si el talonario no tiene ventas (409 en caso contrario, y la FK `ventas.talonario_id` es `RESTRICT`); un talonario que ya emitió se desactiva.

#### Cómo se numera una venta (`POST /api/ventas`)

`talonarioId` es **opcional** en el body. `resolverTalonarioParaVenta` decide, contra los talonarios activos asignados al usuario autenticado para ese tipo de comprobante:

| Situación                                | Resultado                                                                              |
| ---------------------------------------- | -------------------------------------------------------------------------------------- |
| `talonarioId` indicado y disponible      | Se usa ese                                                                             |
| `talonarioId` indicado pero no asignado  | 400 "El talonario indicado no está disponible para este usuario y tipo de comprobante" |
| Sin `talonarioId`, un solo talonario     | Se resuelve solo (la UI ni siquiera muestra un combo)                                  |
| Sin `talonarioId`, varios talonarios     | 400 "Tienes varios talonarios para este comprobante: elige uno"                        |
| Sin `talonarioId`, todos agotados        | 409 con el mensaje de agotado — **nunca** cae a la serie fija a escondidas             |
| El usuario no tiene **ningún** talonario | `null` → serie fija `B001`/`F001`, la numeración anterior al módulo                    |

- **Atomicidad**: reservar el correlativo, guardar la venta con sus detalles y consumir el talonario ocurren en una sola transacción (`AppDataSource.transaction` en `crearVenta`). `reservarNumero` bloquea la fila con `SELECT … FOR UPDATE` (`lock: pessimistic_write`, sin `relations` para no romper el lock con un LEFT JOIN), de modo que dos cajeros simultáneos sobre la misma serie se serializan. Verificado con 8 ventas en paralelo: 8 correlativos distintos y consecutivos.
- **Correlativo ya ocupado**: si aun así el número resultara tomado (dos talonarios distintos con la misma serie, o un comprobante insertado por fuera del sistema), la venta **no se pierde**: el índice único `IDX_un_correlativo_por_serie` la rechaza, `guardarReintentandoColision` la vuelve a numerar con el siguiente libre (hasta 3 intentos) y devuelve la venta con su número definitivo. La primera venta conserva su número. El frontend compara el número emitido con el que mostraba y avisa al cajero si cambió, porque el comprobante impreso ya no lleva el número que tenía a la vista.
- **Agotado**: emitir cuando el siguiente número supera `numeroFin` devuelve 409 "El talonario X llegó a su último número autorizado (N). Registra un talonario nuevo."
- **Anular una venta no devuelve el número** al talonario: el correlativo emitido se conserva, como ya hacía Ventas (`estado = anulada`, nunca borrado).
- `ventas.talonario_id` es nullable: las ventas emitidas antes de este módulo no pertenecen a ningún talonario.

### Créditos y cobranzas

Una venta con `formaPago: "credito"` no se cobra al emitirse: queda como **documento por cobrar** y se amortiza con uno o varios pagos.

- **Cronograma (`cuotas_venta`)**: la RS 193-2020/SUNAT obliga a que un comprobante al crédito consigne el monto pendiente y el detalle de cada cuota. `POST /api/ventas` acepta `fechaPrimerVencimiento` y `numeroCuotas` (1 a 36, mensuales); si no se envían, se genera **una cuota única a 30 días** — una venta al crédito nunca queda sin cronograma. El reparto es en partes iguales y la última cuota absorbe el redondeo, de modo que las cuotas suman exactamente el total.
- **Saldo**: no se guarda en `ventas`. Se calcula sumando los pagos no anulados (`cobranza.service.ts: armarVista`), única forma de que no se desincronice al anular un cobro o una venta.
- **Estado de cobranza** (derivado, no persistido): `pendiente` (sin cobros) → `parcial` → `pagada`; `vencida` si queda saldo y la primera cuota impaga ya venció. `diasVencido` cuenta el atraso de esa cuota.
- **Cobros (`pagos_venta`)**: `fechaPago`, `monto`, `medioPagoId`, y `bancoId` + `numeroOperacion` si el medio lo exige. Se rechaza un monto mayor al saldo (400) y cualquier cobro sobre una venta al contado, anulada o ya cancelada. La venta se bloquea con `FOR UPDATE` durante el registro: dos cajeros cobrando el mismo documento a la vez no pueden dejarlo sobrepagado.
- **Anular un cobro** (`DELETE /api/pagos-venta/:id`, body `{ motivo }`) marca `anulado` y conserva la fila con su motivo; el saldo vuelve a subir solo, porque se recalcula.

#### Sustento bancario (Ley 28194)

La bancarización obliga a canalizar por el sistema financiero las operaciones desde S/ 2,000 o US$ 500, dejando constancia de la entidad y el número de operación.

- **Qué medios lo exigen** es un dato del catálogo, `medios_pago.requiere_banco` (hoy: transferencia, depósito en cuenta, cheque) — no una lista de códigos en el código fuente, así agregar un medio bancarizado no obliga a tocar la validación ni la UI.
- **Al contado**: el banco va en la propia venta (`ventas.banco_id`, `numero_operacion`), porque el dinero entró en ese momento.
- **Al crédito**: va en cada `PagoVenta`, no en la venta — el dinero entra después y puede entrar por varias vías distintas.
- Falta el banco o el número de operación cuando el medio lo exige → 400 con el mensaje del medio concreto ("Un pago por depósito en cuenta requiere el banco").
- `bancos` se siembra con las entidades del sistema financiero peruano y su **código SBS**, el mismo del Catálogo N° 54 de SUNAT.

### Reservas de mesa (FASE 11.5)

- **Reglas de negocio** (`reserva.service.ts`): el cliente y la mesa deben existir y estar activos; `cantidadPersonas` no puede exceder `mesa.capacidad`; `fechaHora` debe ser futura; y no puede haber otra reserva **pendiente o confirmada** para la misma mesa cuyo rango `[fechaHora, fechaHora + duracionMinutos)` se solape con el nuevo — el solape se calcula con una condición SQL sobre `fecha_hora` y `duracion_minutos` (`reserva.fecha_hora + (duracion_minutos || ' minutes')::interval > :inicio`), no en memoria.
- **Estados** (`estado`, enum de Postgres): `pendiente` (por defecto) → `confirmada` → `completada`, o `cancelada` desde pendiente/confirmada. `DELETE /api/reservas/:id` es azúcar sintáctica para "poner `estado = cancelada`" (mismo patrón de borrado lógico que Personal/Usuarios/Clientes, aplicado aquí al ciclo de vida de la reserva en vez de a un campo `activo`).
- Body de `POST`/`PUT`: `clienteId`, `mesaId`, `fechaHora` (ISO 8601 **con offset/zulu**, ej. `2026-09-09T19:00:00.000Z` — ver nota de frontend abajo), `duracionMinutos` (opcional, default 90), `cantidadPersonas`, `notas` (opcional), y en `PUT` también `estado`.

### Pedidos de mesa (FASE 12)

- **Alcance de esta fase**: un `Pedido` es la orden de una mesa mientras se atiende (Pedidos + Detalle de pedidos, sección 1 de `CLAUDE.md`). Los estados de cocina/comanda (FASE 13) y el cobro/pago (FASE 14, Ventas) son fases futuras separadas y **no** se adelantan aquí — `estado` de Pedido solo modela "abierto → cerrado" o "abierto → cancelado", sin pasos intermedios de preparación.
- **Estados** (`estado`, enum de Postgres): `abierto` (por defecto, al crear) → `cerrado` (ya no admite cambios; lo hará FASE 14 al facturar), o `cancelado` desde `abierto`. `DELETE /api/pedidos/:id` es azúcar sintáctica para "cancelar" (mismo patrón que Reservas).
- **Reglas de negocio** (`pedido.service.ts`):
  - La mesa debe existir y estar activa; no puede haber **dos pedidos `abierto` simultáneos para la misma mesa** (409 si ya hay uno).
  - Un pedido solo admite agregar/editar/quitar líneas de detalle mientras está `abierto` (400 en cualquier otro estado).
  - No se puede pasar a `cerrado` sin al menos 1 línea de detalle (400).
  - Cada línea (`DetallePedido`) guarda un **snapshot del precio del producto** al momento de agregarla (`precioUnitario`) — si el precio del producto cambia después, no afecta pedidos ya creados. `subtotal = cantidad × precioUnitario`, recalculado en cada cambio de cantidad; `Pedido.total` se recalcula sumando todos los `subtotal` cada vez que una línea se agrega, edita o quita.
  - El producto de una línea debe existir y estar activo al momento de agregarla.
- Body de `POST /api/pedidos`: `mesaId`, `clienteId` (opcional), `notas` (opcional). `PUT /api/pedidos/:id`: `notas` y/o `estado` (solo transición `abierto→cerrado` permitida por esta vía; `cancelado` va por `DELETE`).
- **Mesa reservada (2026-09-08):** al crear un pedido, si la mesa tiene una reserva `pendiente`/`confirmada` cuyo rango `[fechaHora, fechaHora + duracionMinutos)` cubre el momento actual, la mesa está "reservada" en ese instante. Si el `clienteId` del pedido no coincide con el cliente de esa reserva (o no se envía `clienteId`), se rechaza con `409` y un mensaje indicando para quién y a qué hora está reservada. Esto no reemplaza ni modifica el módulo de Reservas — es una validación cruzada de solo lectura en `pedido.service.ts` (`obtenerReservaActivaDeMesa`, consulta directa a `reservaRepository`).
- Body de `POST /api/pedidos/:id/detalles`: `productoId`, `cantidad`, `notas` (opcional). `PUT .../detalles/:detalleId`: `cantidad` y/o `notas`.
- Rutas anidadas: `validateUuidParam(nombre)` (nuevo en `validate.middleware.ts`) valida un parámetro de ruta distinto de `id` (ej. `detalleId`), complementando a `validateIdParam` que solo cubre `id`.
- **Bug real encontrado y corregido (E2E, 2026-09-08):** `obtenerPedido` no ordenaba explícitamente `detalles` al consultarlos — Postgres no garantiza el orden de un `SELECT` sin `ORDER BY`, y tras un `UPDATE` una fila editada puede devolverse en una posición distinta a la de inserción aunque su `creado_en` no cambie. Esto hacía que las líneas del pedido "saltaran" de lugar en la tabla del frontend al editar una cantidad. Fix: `pedido.service.ts` ordena `pedido.detalles` por `creadoEn` ascendente en memoria antes de devolver el pedido.
- **Pedidos "para llevar" — mesa opcional (2026-09-09, pedido del usuario: "que no dependa únicamente de que haya una mesa disponible"):** `mesaId` pasa de obligatorio a opcional en `POST /api/pedidos`; `pedidos.mesa_id` es ahora `NULL`able en la BD (migración `PedidoMesaVentaPedidoOpcionales`). Sin `mesaId` el pedido queda sin mesa asignada ("para llevar") y **ninguna de las validaciones de mesa aplica**: no hay chequeo de "la mesa ya tiene un pedido abierto" (pueden coexistir cuantos pedidos "para llevar" se quiera) ni de reserva activa — esas reglas solo corren cuando sí se indica `mesaId` (`crearPedido` en `pedido.service.ts`). El resto del ciclo de vida (agregar líneas, enviar a cocina, cerrar, cancelar) es idéntico con o sin mesa. Frontend: el modal "Nuevo pedido" (`Pedidos.tsx`) antepone un selector "En el local" / "Para llevar" (`TarjetaOpcion`, ver `frontend.md`) que muestra u oculta el combo de mesa; toda la UI que antes leía `pedido.mesa.numero` directamente ahora pasa por `utils/formato.ts: nombreMesa()`, que devuelve `"Para llevar"` cuando no hay mesa.

### Comandas y cocina (FASE 13)

- **Concepto**: una `Comanda` es un ticket de cocina — un grupo de líneas de un mismo pedido (`DetallePedido`) que el mesero envía a preparar juntas. No toda línea de un pedido tiene por qué estar en una comanda: `detalle_pedidos.comanda_id` es **nullable**; `null` significa "todavía no enviada a cocina". Esto permite enviar el pedido en oleadas (ej. entradas primero, plato de fondo después) en vez de forzar a enviar todo junto.
- **Estados** (`estado`, enum de Postgres): `pendiente` (recién creada, en cola) → `en_preparacion` → `listo` → `entregado`, o `cancelada` desde `pendiente` únicamente (una vez que la cocina empezó a prepararla, ya no se puede cancelar — solo seguir el flujo hasta `entregado`). `PUT /api/comandas/:id` solo permite avanzar **un paso a la vez** en ese orden (400 "Transición de estado no permitida" si se intenta saltar pasos o retroceder). `DELETE /api/comandas/:id` es la cancelación.
- **Cancelar una comanda pendiente libera sus líneas**: vuelven a tener `comanda_id = null`, por lo que el pedido puede volver a editarlas/quitarlas o enviarlas en una comanda nueva.
- **Reglas de negocio** (`comanda.service.ts`): el pedido debe existir y estar `abierto`; todas las líneas indicadas (`detalleIds`) deben existir, pertenecer a ese pedido, y no estar ya asignadas a otra comanda (409 si alguna ya fue enviada).
- **Body de `POST /api/comandas`**: `pedidoId`, `detalleIds` (array de uuid, mínimo 1), `notas` (opcional). `PUT /api/comandas/:id`: `estado`.
- **Impacto cruzado en Pedidos** (`pedido.service.ts`): una línea con `comanda` asignada ya no se puede editar ni quitar desde `PUT`/`DELETE /api/pedidos/:id/detalles/:detalleId` (400 "No se puede modificar un producto ya enviado a cocina") — evita que el mesero cambie algo que la cocina ya está preparando. Tampoco se puede **cerrar** ni **cancelar** un pedido mientras tenga alguna comanda en `pendiente`/`en_preparacion`/`listo` (400) — solo cuando todas sus comandas están `entregado` o `cancelada`.
- **Permisos**: `cocina.ver` (consultar la cola), `cocina.editar` (avanzar estado), `cocina.eliminar` (cancelar pendiente); enviar a cocina (`POST /api/comandas`) usa el permiso existente `pedidos.editar`, no uno nuevo — conceptualmente es una acción sobre el pedido, no sobre la cocina todavía.

### Ventas y pagos (FASE 14)

- **Alcance de esta fase**: `Venta` registra el comprobante emitido a partir de un `Pedido` ya `cerrado` — serie/correlativo, cálculo de IGV por línea, forma y medio de pago. **Explícitamente fuera de alcance** (decisión confirmada con el usuario antes de implementar, ver `decisiones-tecnicas.md`): emisión electrónica real a SUNAT (XML/UBL, firma digital, envío a un PSE/OSE — sigue siendo la "Facturación electrónica SUNAT" que la sección 1 de `CLAUDE.md` marca como ampliación futura), notas de crédito/débito reales, detracciones/percepciones/retenciones, y Caja (apertura/cierre/arqueo — eso es FASE 15, separada; Venta solo dice cómo se pagó, no gestiona una caja física).
- **Catálogos nuevos**: `tipos_afectacion_igv` (Catálogo SUNAT N° 07 — Gravado/Exonerado/Inafecto), `tipos_operacion` (Catálogo SUNAT N° 17 — Venta interna, exportación...), `medios_pago` (catálogo **propio**, no numerado por SUNAT: Efectivo, Tarjeta de crédito, Tarjeta de débito, Transferencia, Yape, Plin — SUNAT no define un catálogo oficial para el instrumento de pago en boletas/facturas comunes). `Producto` ahora tiene `tipoAfectacionIgv` obligatorio (default `Gravado` para los productos ya existentes, vía migración con backfill igual que `unidad_medida_id` en su momento).
- **Cálculo de IGV** (`venta.service.ts`): el precio de un producto se trata como precio final **con IGV incluido** (18%: 16% IGV + 2% IPM, tasa hardcodeada en `TASA_IGV`, con comentario explícito de dónde cambiarla si SUNAT ajusta la tasa). Para una línea `Gravada`: `valorVenta = subtotalLínea / 1.18` (redondeado a 2 decimales), `igv = subtotalLínea - valorVenta`. Para `Exonerado`/`Inafecto`: `valorVenta = subtotalLínea`, `igv = 0`. `Venta.total` siempre coincide con `Pedido.total` (no se recalcula independientemente); `Venta.subtotal`/`Venta.igv` son la suma de las líneas.
- **Snapshot de línea** (`DetalleVenta`): cada línea de una venta copia `descripcionProducto`, `precioUnitario` y `tipoAfectacionIgv` del `DetallePedido` de origen al momento de facturar — si el producto cambia de precio o de afectación después, la venta ya emitida no se altera (mismo criterio que `DetallePedido` respecto a `Producto`).
- **Reglas de negocio** (`venta.service.ts`):
  - Solo se puede crear una venta desde un pedido `cerrado` (400 en cualquier otro estado), y solo una vez por pedido (409 si ya existe una venta para ese `pedidoId`, sin importar si esa venta está `anulada`).
  - Solo se pueden emitir **Boleta** (código SUNAT `03`) o **Factura** (código `01`) desde este módulo — cualquier otro `tipoComprobanteId` del catálogo (notas de crédito/débito, guía de remisión) se rechaza con 400.
  - **Factura exige cliente con RUC**: sin `clienteId` → 400; con `clienteId` pero el cliente no tiene `tipoDocumentoIdentidad` = RUC (código `6`) → 400. Boleta no exige cliente.
  - **Serie fija por tipo de comprobante** (no configurable desde la UI, restaurante de un solo local): Boleta → `B001`, Factura → `F001`. El correlativo (`numero`) es `MAX(numero) WHERE tipo_comprobante_id = X AND serie = Y` + 1 (empieza en 1); único índice compuesto `(tipo_comprobante_id, serie, numero)` como respaldo ante condiciones de carrera (poco probable en un solo punto de venta, pero la constraint de BD evita un duplicado silencioso).
  - **Forma de pago** (`Contado`/`Crédito`, enum de Postgres, default `Contado`) y **medio de pago**: si `formaPago = Contado`, `medioPagoId` es obligatorio (400 si falta); si es `Crédito`, el medio de pago queda `null` (se paga después, no hay instrumento todavía).
  - **Tipo de operación**: opcional en el body; si no se envía, se usa por defecto el catálogo `0101 - Venta interna` (el único caso real en un restaurante de un solo local con ventas presenciales) — la UI no expone este campo para no añadir complejidad sin necesidad.
  - **Anular** (`DELETE /api/ventas/:id`) solo cambia `estado` a `anulada` (nunca borrado real, preserva el número correlativo ya emitido tal como exige la normativa); una venta ya `anulada` no se puede volver a anular (400). Anular una venta **no reabre** el pedido original — son conceptos independientes una vez emitido el comprobante.
- **Body de `POST /api/ventas`**: `pedidoId`, `tipoComprobanteId`, `clienteId` (opcional salvo Factura), `tipoOperacionId` (opcional), `formaPago` (opcional, default `contado`), `medioPagoId` (opcional salvo forma de pago Contado).
- **Permisos**: nombrados tal como los da el ejemplo de la sección 10 de `CLAUDE.md` — `ventas.ver`, `ventas.crear`, `ventas.anular` (no `.eliminar`, único módulo del proyecto con esa excepción deliberada).
- **Tipo de cambio (2026-09-08)**: al crear la venta, `venta.service.ts` consulta el tipo de cambio USD/PEN publicado por SUNAT para la fecha de emisión (`catalogos/tipo-cambio.service.ts`, mismo proveedor Decolecta que la consulta de documentos: `GET /v1/tipo-cambio/sunat?date=YYYY-MM-DD`) y lo guarda en `ventas.tipo_cambio` (el "precio venta" del tipo de cambio, el que usa SUNAT para operaciones en moneda extranjera). Es **solo de referencia contable** — todas las ventas de este sistema se cobran en soles; si la consulta falla por cualquier motivo (sin token, proveedor caído, timeout), la venta igual se registra con `tipo_cambio = null`, nunca se bloquea la venta por esto.
- **Frontend — visibilidad del comprobante (2026-09-08)**: `/ventas` muestra columnas separadas de Comprobante (serie-correlativo, ej. `B001-000001`), Fecha de emisión, Mesa, Cliente, Subtotal, IGV, Total y Estado; al hacer clic en el comprobante (o el botón "Ver") se abre un modal tipo recibo con el desglose completo por línea y el tipo de cambio si está disponible.
- **Venta directa — sin depender de un pedido (2026-09-09, pedido del usuario: "que no dependa únicamente de que haya un pedido disponible... que se pueda agregar productos nada más"):** `pedidoId` pasa de obligatorio a opcional en `POST /api/ventas`; `ventas.pedido_id` es ahora `NULL`able (misma migración que Pedidos). El body admite **exactamente uno** de estos dos orígenes, validado con `crearVentaSchema.refine()` en `venta.dto.ts` (400 "Indica un pedido cerrado a facturar o una lista de productos, no ambos" si se envían los dos o ninguno):
  - `pedidoId` — el flujo original: copia (snapshot) las líneas del pedido cerrado, igual que antes.
  - `detalles: [{ productoId, cantidad }]` (1 a 50 líneas) — **venta directa**: cada línea se resuelve contra el catálogo de productos vigente (debe existir y estar activo) exactamente igual que `agregarDetalle` de Pedidos, y su snapshot (`descripcionProducto`, `precioUnitario`, `tipoAfectacionIgv`) queda directamente en `detalle_ventas` sin que exista nunca un `Pedido`/`DetallePedido` de por medio. El desglose de IGV usa la misma función (`calcularLinea`) para ambos orígenes, así la regla fiscal no se bifurca según de dónde vino la línea.
  - En una venta directa `venta.pedido` queda `null`; el resto del comprobante (comprobante, cliente, forma/medio de pago, tipo de cambio, numeración) es idéntico a una venta desde pedido.
  - **Por qué no hace falta un índice parcial:** Postgres no considera iguales dos valores `NULL` en una columna `UNIQUE`, así que el índice único ya existente sobre `ventas.pedido_id` (que impide dos ventas del mismo pedido) admite cualquier cantidad de ventas directas sin modificarse — verificado insertando dos filas con `pedido_id = NULL` dentro de una transacción de prueba (revertida).
  - Frontend: el modal "Nueva venta" (`Ventas.tsx`) antepone un selector "Desde un pedido" / "Venta directa" (`TarjetaOpcion`, compartido con Pedidos); el modo directo agrega un mini-carrito (Combobox de producto + cantidad + lista editable con `useFieldArray` de react-hook-form) con un total estimado que coincide exactamente con lo que calculará el backend (`Σ precio × cantidad`, sin desglosar IGV en el cliente). El modo "Desde un pedido" gana un panel de vista previa con las líneas y el total del pedido elegido, antes inexistente.
  - **"Pull" de consumo desde una mesa (parte del mismo pedido del usuario):** no se agregó un campo `venta.mesa` nuevo — el combo "Pedido a facturar" del modo "Desde un pedido" ya etiqueta cada opción por su mesa (`nombreMesa(pedido.mesa)`, "Para llevar" si no tiene), así que elegir por mesa y elegir por pedido son la misma acción; añadir un campo aparte hubiera duplicado ese mismo dato sin necesidad.

### Caja: apertura, cierre y movimientos (FASE 15)

- **Alcance**: `Caja` es una sesión de arqueo (turno), independiente de `Venta` — Ventas solo dice cómo se pagó cada comprobante, Caja controla el efectivo físico del turno. Solo puede existir **una caja `abierta` a la vez en todo el sistema** (restaurante de un solo local, sección 1 de `CLAUDE.md`): garantizado con un índice único parcial de Postgres sobre `cajas.estado` (`WHERE estado = 'abierta'`), no solo con el chequeo en `caja.service.ts` — evita que dos "abrir caja" simultáneas dejen dos sesiones abiertas por una condición de carrera.
- **No se tocó el módulo Ventas** (Regla 3 de `CLAUDE.md`): no se agregó un `caja_id` a `ventas`. Para saber cuánto efectivo entró durante una sesión, `caja.service.ts` consulta `Venta` por rango de fecha (`creadoEn` entre la apertura y el cierre) y medio de pago = "Efectivo" (`medioPago.codigo === 'efectivo'`, catálogo de FASE 14) en el momento de cerrar. Es la misma información, reconstruida sin duplicar estado ni acoplar los dos módulos.
- **Campos de `Caja`**: `montoApertura` (obligatorio al abrir), `montoEsperado` y `diferencia` quedan `null` hasta el cierre — se calculan y **congelan** en ese momento (`montoEsperado = montoApertura + ventas en efectivo del turno + ingresos manuales − egresos manuales`; `diferencia = montoDeclarado − montoEsperado`). Congelarlos evita que anular una venta después del cierre altere un arqueo ya hecho. `usuarioApertura`/`usuarioCierre` se toman de `req.usuarioAuth.sub` (el usuario autenticado), no del body — no se puede abrir o cerrar "en nombre de otro".
- **`MovimientoCaja`**: ingreso o egreso manual dentro de una sesión abierta (ej. compra menor, vuelto entregado de más) — no incluye las ventas en efectivo, que se calculan aparte. Es un registro inmutable (sin `actualizadoEn`, igual que `DetalleVenta`); muere en cascada con su `Caja` (`onDelete: 'CASCADE'`, a diferencia de las relaciones a catálogos/entidades de negocio, que son `RESTRICT`).
- **Reglas de negocio** (`caja.service.ts`): `abrirCaja` rechaza con 409 si ya hay una caja abierta; `registrarMovimiento`/`cerrarCaja` rechazan con 400 si la caja indicada no está `abierta`; `cerrarCaja` rechaza con 400 si ya está `cerrada` (no se puede volver a cerrar).
- **Endpoints**: `GET /api/cajas` (historial), `GET /api/cajas/actual` (la sesión abierta o `null` — registrada **antes** de `GET /api/cajas/:id` en `caja.routes.ts`, si no Express trataría `"actual"` como un `:id`), `GET /api/cajas/:id`, `POST /api/cajas/abrir` (`{ montoApertura, observacion? }`), `POST /api/cajas/:id/cerrar` (`{ montoDeclarado, observacion? }`), `POST /api/cajas/:id/movimientos` (`{ tipo: 'ingreso'|'egreso', monto, concepto }`).
- **Permisos**: `caja.ver`, `caja.abrir`, `caja.cerrar` — nombrados tal como los da el ejemplo de la sección 10 de `CLAUDE.md`. Registrar un movimiento reutiliza `caja.abrir` (interpretado como "operar una caja ya abierta") en vez de inventar un cuarto código que `CLAUDE.md` no predefine para este módulo — ver `decisiones-tecnicas.md`.
- **Frontend**: `/caja` (`pages/Caja.tsx`) muestra la sesión abierta como una tarjeta destacada con el efectivo esperado **estimado en vivo** (recalculado en el cliente con el mismo criterio que el backend usa al cerrar, mediante la caché ya cargada de `['ventas']` — el número que realmente se guarda lo calcula y congela el backend recién al cerrar), tarjetas KPI (apertura/ventas en efectivo/ingresos/egresos), un panel "Ventas por medio de pago" (todos los medios, no solo efectivo, más las ventas al crédito de la sesión — feedback del usuario tras la primera versión, ver `frontend.md`), la lista de movimientos del turno con botón para registrar uno nuevo, e historial de sesiones anteriores con el detalle de cada arqueo. El modal de cierre muestra una vista previa reactiva de sobrante/faltante mientras el cajero escribe el monto contado, antes de confirmar.
- **Bug real encontrado y corregido (2026-09-09):** `utils/numeric-transformer.ts` (compartido por todas las columnas `numeric` del proyecto) convertía `null` en `0` en cualquier columna anulable (`Number(null) === 0`) — afectaba a `cajas.monto_esperado`/`monto_declarado`/`diferencia` antes del cierre y a `ventas.tipo_cambio`. Detectado al inspeccionar en vivo una sesión de caja real todavía abierta. Fix: el `from` del transformer ahora preserva `null` explícitamente. Ver `frontend.md` para el detalle completo.

### Inventario: mercadería vs. servicio, kardex y descuento por receta (FASE 16)

- **Alcance del pedido del usuario**: "que se separen mercaderías y servicios (gaseosas/insumos vs. platillos), una tabla `existencias` con todos los movimientos de un producto (compra, venta, stock inicial, almacén de origen/destino, fecha), y que cada platillo descuente sus insumos". Se implementó como Kardex normalizado (un movimiento por fila, no columnas anchas de "stock compra"/"stock venta" en la misma fila — es el diseño estándar de un libro de inventario y evita que dos eventos independientes intenten escribir la misma fila).
- **`Producto.tipo`** (`mercaderia` | `servicio`, nuevo enum, default `servicio` por backfill): la misma distinción que ya separan `tipos_afectacion_igv`/`tipos_operacion` para SUNAT, aplicada al stock — `mercaderia` se vende tal cual (ej. una gaseosa embotellada) y tiene stock propio en `existencias`; `servicio` se prepara (ej. un platillo) y **no** tiene stock propio, descuenta el de sus insumos vía `RecetaInsumo`. **Los 2 productos ya existentes al migrar quedaron en `servicio` por el backfill** — si alguno es en realidad una mercadería (ej. una gaseosa embotellada), hay que cambiarle el tipo a mano desde `/productos` después de esta migración; no había forma de inferirlo automáticamente.
- **`Insumo`** (`modules/insumos`): materia prima que nunca se vende directamente (harina, pollo, aceite…) — por eso no es un `Producto` (que sí aparece en la Carta), es un catálogo propio con solo nombre/descripción/unidad de medida. "Eliminar" es borrado lógico (`activo = false`), igual que Usuarios/Personal/Clientes: un insumo ya puede tener movimientos en `existencias` o estar en la receta de un producto.
- **`RecetaInsumo`** (`modules/recetas`, tabla `receta_insumos`): una línea por `(producto, insumo)` con `cantidad` (la que consume **una** unidad del producto, en la unidad de medida del insumo) — único índice compuesto para no repetir el mismo insumo dos veces en una receta. `PUT /api/recetas/:productoId` reemplaza la receta completa (borra las líneas anteriores e inserta las nuevas: más simple que un diff línea por línea, y una receta no cambia con frecuencia suficiente para que el costo importe). Reutiliza los permisos `productos.ver`/`productos.editar` — una receta es parte de la definición de un producto, no un recurso propio.
- **`Almacen`** (`modules/almacenes`): pertenece a una `Empresa` (FK). Un solo almacén puede marcarse `esPrincipal` por empresa — es el destino/origen por defecto de los movimientos automáticos —, garantizado con un índice único parcial de Postgres (`WHERE es_principal = true`), mismo patrón que la caja única abierta de FASE 15. Al marcar uno como principal, el service despriorriza automáticamente cualquier otro de la misma empresa (se siente como "mover" la marca, no como un error).
- **`Existencia`** (`modules/inventario`, tabla `existencias`): el kardex. Cada fila tiene `tipo` (`inicial`/`compra`/`ajuste_entrada`/`ajuste_salida`/`consumo_cocina`/`venta_directa`), `cantidad` (siempre positiva; la dirección la da `tipo`), `almacen`, y **exactamente uno** de `insumo`/`producto` — impuesto con un `CHECK` de Postgres (`(insumo_id IS NULL) != (producto_id IS NULL)`), no solo validado en el DTO. El saldo de un ítem en un almacén se calcula agregando en SQL (`SUM` con signo según `tipo`), no se guarda como columna: un kardex real acumula muchas filas, y la agregación en la propia base es más barata que traer todo el historial a memoria.
- **Cuándo se descuenta el stock de un platillo — decisión tomada junto con el usuario**: no al facturar la venta, sino **al entregar la comanda** (`comanda.service.ts: actualizarEstadoComanda`, transición a `entregado`) — es el momento en que el insumo físicamente se usó en cocina, antes de que exista ningún comprobante. Para cada línea de la comanda: si el producto es `servicio`, se multiplica la `cantidad` de cada línea de su receta por la cantidad vendida y se crea un movimiento `consumo_cocina` por insumo; si es `mercaderia` (ej. una bebida que igual pasó por cocina), se descuenta su propio stock. **Una línea de pedido que nunca pasó por cocina** (venta directa sin pedido, o una línea de un pedido que se facturó sin enviarla a cocina) se descuenta recién al emitir la venta (`venta.service.ts: crearVenta`, mismo tipo `venta_directa`) — nunca antes, porque no hay forma de saber que se va a vender hasta ese momento.
- **Por qué facturar un pedido no vuelve a descontar stock**: un pedido no puede cerrarse mientras tenga una comanda en `pendiente`/`en_preparacion`/`listo` (regla ya existente de FASE 13), así que al momento de facturar, toda línea que sí se envió a cocina ya está `entregado` (con su `consumo_cocina` ya registrado) o su comanda se canceló (`comanda_id` vuelve a `null`, cae en el caso "nunca pasó por cocina"). `venta.service.ts` distingue ambos casos por `detalle.comanda`: si no es `null`, solo enlaza el `venta_id` a los movimientos `consumo_cocina` ya existentes de ese pedido (trazabilidad: "qué comprobante terminó pagando este consumo"), sin crear una fila nueva; si es `null`, recién ahí crea el movimiento `venta_directa`. Verificado con un pedido real de principio a fin: comanda entregada → stock baja exactamente lo que dice la receta → factura el mismo pedido → el stock **no vuelve a bajar**, solo se enlaza el movimiento existente a la venta.
- **Sin almacén principal configurado, los movimientos automáticos simplemente no se registran** (`obtenerAlmacenPorDefecto` devuelve `null`) — no bloquea Pedidos/Cocina/Ventas, que deben seguir funcionando igual para quien no haya configurado Inventario todavía (mismo criterio de degradación que `obtenerEmpresaPublica`/`consultarTipoCambio`).
- **No se agregó `caja_id` a `existencias`**, aunque conceptualmente ambos módulos "muevan cosas": son ejes independientes (efectivo vs. stock) y cruzarlos no lo pidió el usuario.
- **Explícitamente fuera de alcance de esta fase** (quedan para las suyas, ya previstas en `plan-fases.md`): un módulo completo de Proveedores/Compras (FASE 17 — hoy `POST /api/existencias/movimientos` con `tipo: compra` es un registro manual sin proveedor asociado, suficiente para dar de alta stock); costeo/margen por platillo a partir del costo de sus insumos (FASE 18 — la receta y el `costoUnitario` de cada compra ya quedan registrados, listos para esa fase); bloquear una venta si no alcanza el stock (no se pidió, y bloquear ventas por un módulo nuevo que muchos restaurantes todavía no configuran habría sido una regresión sorpresa — el stock simplemente puede quedar en negativo, visible en `/inventario`).
- **Endpoints**: `GET/POST/PUT/DELETE /api/insumos`, `GET/POST/PUT/DELETE /api/almacenes`, `GET/PUT /api/recetas/:productoId`, `GET /api/existencias/stock` (saldo consolidado por ítem y almacén), `GET /api/existencias/movimientos` (kardex, filtrable por `almacenId`/`insumoId`/`productoId`), `POST /api/existencias/movimientos` (`{ almacenId, insumoId | productoId, tipo: 'inicial'|'compra'|'ajuste_entrada'|'ajuste_salida', cantidad, costoUnitario?, observacion? }` — solo estos 4 tipos son registrables a mano; `consumo_cocina`/`venta_directa` los dispara el flujo, nunca este endpoint).
- **Permisos**: `almacenes.ver/.crear/.editar/.eliminar`, `insumos.ver/.crear/.editar/.eliminar` (patrón genérico, sin ejemplo propio en la sección 10 de `CLAUDE.md`); `inventario.ver`/`inventario.ajustar` (nombrados tal como los da esa sección).
- **Detalle no obvio en `venta.service.ts: crearVenta`:** para poder distinguir una línea de pedido ya consumida en cocina (no se debe volver a descontar) de una que nunca se envió a cocina (sí hay que descontarla al facturar), la consulta del pedido tuvo que ampliarse para cargar también `detalles.comanda` (antes solo cargaba `detalles.producto`) — sin ese dato, `registrarConsumoVenta` no tiene cómo saber si ya hubo un `consumo_cocina` para esa línea.
- **Bug real encontrado y corregido (2026-09-09):** `receta.service.ts: reemplazarReceta` fallaba con 400 "Uno o más insumos indicados no existen" al vaciar una receta (`lineas: []`) — `insumoRepository.findBy([])` con un arreglo vacío de condiciones no filtra nada en TypeORM, devuelve **todos** los insumos en vez de ninguno, así que la comparación `insumos.length !== idsInsumos.length` (`N !== 0`) siempre disparaba el error. Se detectó al limpiar los datos de prueba de la verificación de esta misma fase. Fix: cortar antes de consultar cuando `idsInsumos.length === 0`.

### Configuración operativa del restaurante (FASE 21)

- **`GET /api/configuracion`** y **`PUT /api/configuracion`** (permisos `configuracion.ver` / `configuracion.editar`). Es un recurso **singular**: no hay una lista de configuraciones, hay _la_ configuración de la empresa, que sale del token como en todo el resto de la API.
- **Leer no crea la fila.** Si la empresa nunca guardó su configuración, el service devuelve `CONFIGURACION_POR_DEFECTO` sin escribir nada. Una petición GET no debería tener efectos secundarios, y así tampoco hace falta sembrar una fila por cada empresa nueva ni hacer un backfill para las existentes. La fila nace con el primer `PUT`.
- **Qué contiene**: lo que hasta esta fase eran **constantes escritas en el código** y que cada restaurante quiere distinto — `duracionReservaMinutos` (antes 90 fijo en `reserva.service.ts`), `segundosRefrescoCocina` (antes 8000 ms fijos en `Cocina.tsx`), `diasCreditoPorDefecto` (antes `DIAS_CREDITO_POR_DEFECTO = 30` en `venta.service.ts`), `foodCostObjetivo`/`foodCostCritico` (antes 35 y 50 en `Costos.tsx`) — más los datos que la carta pública necesitaba y no tenía dónde guardar: `horarioAtencion`, `mensajeBienvenida`, `aceptaPedidosWhatsapp` y los enlaces de redes.
- **Tabla tipada, no clave-valor.** Un `configuraciones(clave, valor)` sería más flexible pero pierde el tipo, la validación y el valor por defecto: nada impediría guardar `dias_credito = "treinta"`. Con columnas tipadas validan Postgres y zod por su cuenta, y un `CHECK` garantiza que el food cost crítico siempre sea mayor que el objetivo.
- **El subconjunto público se enumera explícitamente.** `GET /api/publico/:slug/empresa` devuelve horario, mensaje, si acepta pedidos y las redes **junto a** los datos de la empresa (la carta los necesita a la vez; separarlos obligaría a dos viajes de red para pintar la cabecera). Los umbrales de food cost y los días de crédito **no** viajan: son información interna del negocio, no algo que deba llegar al celular de un comensal.
- **`aceptaPedidosWhatsapp: false`** deja la carta como menú de consulta: se ve completa, pero sin la bandeja flotante ni los botones de agregar. Hay locales que solo atienden en salón y publican el menú como referencia.

### Multi-empresa: aislamiento de datos entre restaurantes (FASE 25)

- **Cada petición a `/api` corre dentro de una transacción** que fija `app.empresa_id` (`middlewares/tenant.middleware.ts`). Es la única conexión donde las políticas RLS de Postgres dejan ver algo: sin ese ajuste, **ninguna consulta devuelve filas**.
- **La empresa sale del token firmado**, nunca de una cabecera o del cuerpo. `AccessTokenPayload` gana `empresaId`; `requireAuth` lo aplica con `establecerEmpresaDeLaPeticion`. Los tokens emitidos antes de esta fase no lo traen y se rechazan con 401 "Sesión desactualizada" en vez de adivinar una empresa.
- **Los repositorios cambiaron de `AppDataSource.getRepository(X)` a `tenantRepository(X)`** (27 archivos). Ese proxy hace dos cosas: enruta cada consulta por la transacción de la petición, y estampa la empresa al escribir. **No filtra por `empresa_id` en el `where`** — eso lo hace Postgres, lo que de paso cubre las consultas SQL crudas de Reportes, Costeo y Kardex, que un filtro en TypeScript nunca habría tocado.
- **`AppDataSource.transaction(...)` se reemplazó por `enTransaccion(...)`** en Ventas, Compras y Cobranzas: abría una transacción en **otra** conexión, sin `app.empresa_id`, donde las políticas no habrían dejado ni leer ni escribir.
- **Dos roles de base de datos.** `DB_USER` (dueño, superusuario) solo ejecuta migraciones; `DB_APP_USER` atiende peticiones y **no tiene `SUPERUSER` ni `BYPASSRLS`**. Sin esta separación el aislamiento es decorativo — un superusuario se salta RLS siempre, incluso con `FORCE`. Ver `decisiones-tecnicas.md`.
- **Endpoints públicos de la carta**: `GET /api/empresas/publico` y `GET /api/productos/publico` fueron reemplazados por `GET /api/publico/:slug/empresa` y `GET /api/publico/:slug/productos`. "La empresa pública" dejó de ser una sola.
- **Restricciones únicas que pasaron a ser por empresa**: nombre de categoría/marca/insumo/salón/rol, documento de cliente/proveedor/personal, correo de cliente, caja abierta, y el correlativo `(tipo_comprobante, serie, numero)` de ventas. `usuarios.email` sigue siendo único globalmente a propósito (el login no tiene selector de empresa).
- **Resueltos los tres puntos que asumían un solo restaurante**: `resolverTasaIgv()`, `obtenerEmpresaPublica()` y `obtenerAlmacenPorDefecto()` tomaban "la empresa activa más antigua"; ahora usan la empresa de la petición.

### Cuentas de prueba, suscripción y panel del proveedor (FASE 26)

- **`POST /api/demo/registrar`** (público, 5 por hora y por IP): crea la empresa, el rol Administrador con todos los permisos, el personal, el usuario y el almacén principal, y devuelve la sesión iniciada. Exige RUC (único: una prueba por negocio real). `GET /api/demo/informacion` expone la duración real de la prueba y el contacto del proveedor; `GET /api/demo/tipos-documento` sirve el catálogo SUNAT que el formulario necesita sin sesión.
- **`GET /api/suscripcion`**: estado de la cuenta (`activa` | `demo` | `demo_vencida` | `suspendida`), días restantes y contacto del proveedor. **El vencimiento se deriva de `demoExpiraEn` en cada petición**, no se guarda como estado: así no hace falta una tarea programada ni existe la ventana en que la demo ya venció pero la columna dice lo contrario.
- **Al vencer, la cuenta queda en solo lectura.** Las escrituras responden **402 (Pago requerido)** —no 403, que significaría "no tienes permiso"— con el mensaje de contacto. La lectura sigue abierta para que el restaurante conserve y exporte lo que cargó. El control vive dentro de `requireAuth`, el único punto por el que pasan todas las rutas protegidas.
- **`registros_uso`**: una fila por empresa y día, con peticiones, escrituras y último acceso, acumulada con `INSERT ... ON CONFLICT DO UPDATE` dentro de la transacción que la petición ya tiene abierta. Agregado por día y no por petición a propósito: responde "¿se usa de verdad?" sin crecer sin límite.
- **`GET /api/plataforma/panel`**, `GET /api/plataforma/empresas/:id/uso` y `POST /api/plataforma/empresas/:id/acciones` (`activar` | `extender_demo` | `suspender` | `reactivar`). Es el **único recurso que atraviesa el aislamiento** y corre bajo `conBypassRls`. Se protege con `usuarios.es_proveedor` —activable solo por migración— y no con el catálogo de permisos: ningún rol de un restaurante debería poder contener un permiso que le deje ver a los demás. Responde **404** a quien no es proveedor: no se confirma siquiera que el panel exista.

### Recetas y costos: costo, margen y food cost por producto (FASE 18)

- **Qué agrega sobre FASE 16**: la receta (`receta_insumos`) y el costo de cada compra ya existían; lo que faltaba era convertirlos en el indicador que realmente se usa para decidir precios. `GET /api/costeo` devuelve, por producto activo: `precio` (de carta, con IGV), `valorVenta` (sin IGV), `costo` (neto), `margen`, `margenPorcentaje`, `costoPorcentaje` ("food cost") y el desglose `lineas[]` de su receta. `GET /api/costeo/:productoId` devuelve lo mismo para uno solo.
- **Sin tablas nuevas**: el costeo se recalcula al vuelo en cada consulta, no se persiste un costo "congelado" por producto — el costo real cambia con cada compra, y una tabla de costos guardada quedaría desactualizada en silencio. La foto histórica de lo que costó una venta concreta ya la da el kardex (`existencias`), que sí guarda el costo del momento.
- **El costo usado es NETO de IGV, y no es el mismo número que `Insumo.ultimoCosto`.** `existencias.costo_unitario` guarda el monto _tal como se tipeó en la compra_, que con `Compra.incluyeIgv = true` (el caso normal) trae el IGV adentro. Comparar eso contra el valor de venta sin IGV inflaría el costo y subestimaría el margen. `existencia.service.ts: obtenerCostosNetos()` toma, del movimiento de entrada más reciente de cada ítem, `detalle_compras.valor_compra / cantidad` cuando ese movimiento vino de una `Compra` (ya desglosado según el `tipoAfectacionIgv` del propio ítem), y `existencias.costo_unitario` tal cual cuando fue un movimiento manual — marcando ese caso con `origenCosto: 'manual'` para que la interfaz advierta que el costo no pasó por un comprobante. `obtenerUltimosCostosInsumos()` (bruto) se conserva sin cambios: sigue alimentando la sugerencia de costo al registrar una compra nueva, donde lo que interesa es lo que efectivamente se pagó.
- **Mercadería vs. servicio**: un `servicio` (platillo) se costea sumando su receta; una `mercaderia` (ej. una gaseosa) no tiene receta, su costo es el de su propia última compra.
- **Lo que no se puede costear se dice, no se asume cero**: `motivoSinCosteo` distingue `sin_receta` (un platillo al que nunca se le cargó la receta) de `sin_costos` (hay qué costear, pero ningún componente tiene compra con costo registrado). Un platillo sin receta mostrado como "margen 100%" sería una mentira más peligrosa que un hueco visible. `costoCompleto: false` + `componentesSinCosto[]` marcan el caso intermedio: parte de la receta sí tiene costo, así que el costo mostrado es un piso y el margen está sobreestimado.
- **`resolverTasaIgv()` se movió de `modules/ventas` a `modules/empresa/igv.service.ts`** (junto con `CODIGO_AFECTACION_GRAVADO` y el helper `esGravado`): la tasa es un atributo de la empresa, no de la venta, y ahora la necesitan dos módulos — emitir comprobantes y costear platillos. `venta.service.ts` y `compra.service.ts` la importan de ahí; el cálculo no cambió.
- **Endpoints**: `GET /api/costeo`, `GET /api/costeo/:productoId`. **Permiso**: `costos.ver` (nuevo, migración `SeedPermisoCostos`, otorgado a Administrador).
- **Fuera de alcance de esta fase**: costo promedio ponderado o PEPS (se usa el último costo conocido, que es lo que un restaurante mira para fijar precio), sugerencia automática de precio por margen objetivo, y margen real por venta emitida (eso es analítica de Reportes, no costeo de carta).

### Tasa de IGV configurable por empresa: régimen MYPE de restaurantes (2026-09-09)

- **Contexto**: el usuario preguntó por la tasa de IGV real de un restaurante en Perú. Se verificó contra `orientacion.sunat.gob.pe`: además de la tasa general (18% = 16% IGV + 2% IPM), existe un **régimen especial para MYPE de restaurantes/hoteles/alojamiento turístico** — 10.5% en 2026 (8% IGV + 2.5% IPM; sube a 15% en 2027), amparado en la Ley N° 31940 y prorrogado/ajustado por las Leyes N° 32219 y 32387. **No es automático**: exige que el negocio sea MYPE, facture hasta 1,700 UIT/año, tenga al menos 70% de sus ingresos de esa actividad, no tenga vinculación económica con otro grupo, y se haya acogido explícitamente ante SUNAT (Formulario Virtual 621, Clave SOL).
- **Por qué no es un simple cambio de constante**: distintos restaurantes que usen este sistema pueden o no calificar/haberse acogido — la tasa depende de la situación tributaria de cada empresa, no del sistema. `Empresa` gana `acogidoRegimenMypeRestaurantes: boolean` (default `false`, tasa general); `venta.service.ts: resolverTasaIgv()` la consulta contra la empresa activa antes de armar cada venta (`TASA_IGV_GENERAL = 0.18` vs. `TASA_IGV_MYPE_RESTAURANTES = 0.105`), reemplazando la constante fija `TASA_IGV` que existía desde FASE 14.
- **Impacto en ventas ya emitidas**: ninguno — `Venta.igv`/`subtotal` quedan grabados con la tasa vigente al momento de emitir cada comprobante (snapshot, igual criterio que el resto del sistema); cambiar el régimen de la empresa después no altera ventas pasadas, solo las nuevas.

### Insumo: afectación de IGV propia y costo estimado de receta (2026-09-09, feedback del usuario)

- **Por qué un insumo necesita su propio `tipoAfectacionIgv`, no el del platillo que lo usa**: verificado que el Apéndice I de la Ley del IGV exonera la venta de productos agropecuarios frescos en su estado natural (verduras, frutas) — un insumo comprado fresco suele venir exonerado aunque el platillo preparado con él sí esté gravado. `Insumo` gana `tipoAfectacionIgv` (FK obligatoria al mismo catálogo SUNAT que ya usa `Producto`, sin backfill porque no había insumos creados todavía).
- **Se evaluó fusionar `Insumo` dentro de `Producto`** (un solo catálogo con `tipo: mercaderia | servicio | insumo`) y se descartó: `Producto.categoria` y `Producto.precio` son obligatorios porque todo `Producto` es vendible (aparece en la Carta); un insumo no tiene categoría de carta ni precio de venta, solo un costo de compra que además varía por compra (`Existencia.costoUnitario`). Fusionarlos habría exigido volver esos campos opcionales y filtrar insumos en cada listado/endpoint de `Producto` ya construido (carta pública, Pedidos, Ventas, Comandas, Dashboard). Se mantienen separados; ver `decisiones-tecnicas.md` para el detalle completo de la evaluación.
- **Costo estimado de una receta**: el usuario pidió tener en cuenta que la compra de un insumo "afecta al precio de costo del platillo". `existencia.service.ts: obtenerUltimosCostosInsumos()` calcula, por insumo, el `costoUnitario` de su movimiento de entrada (`compra`) más reciente en cualquier almacén (`SELECT DISTINCT ON (insumo_id) ... ORDER BY insumo_id, creado_en DESC`). `GET /api/insumos` expone ese último costo como `ultimoCosto` (`null` si nunca se compró); `GET/PUT /api/recetas/:productoId` lo enlaza a cada línea de la receta. Es puramente informativo — no calcula margen ni se guarda en ningún lado, y no bloquea nada; el costeo real con margen queda para FASE 18 (Recetas y costos), que ya puede construir sobre este dato en vez de empezar de cero.
- **Detalle de arquitectura para evitar un ciclo de imports**: `existencia.service.ts` ya importaba `receta.service.ts` (para descontar stock según receta); enlazar el costo dentro de `receta.service.ts` habría requerido importar de vuelta `existencia.service.ts`, un ciclo. Se resolvió en `receta.controller.ts` en su lugar — un controller puede depender de ambos services sin problema, a diferencia de un service dependiendo del otro en las dos direcciones.

### Cliente: razón social para persona jurídica (2026-09-08)

- **Regla**: un cliente con RUC que empieza en `20` (persona jurídica / empresa) se identifica por `razonSocial`, nunca por `nombres`/`apellidos` — SUNAT no le asocia esos campos. Cualquier otro cliente (DNI, RUC `10`/`15`/`17` de persona natural, CE, Pasaporte, o sin documento) usa `nombres`/`apellidos` como antes; `razonSocial` queda `null`. Son mutuamente excluyentes, validado en `cliente.service.ts` (`validarNombreORazonSocial`) tanto al crear como al editar (recalculando con el tipo/número de documento final, igual que ya hacía `resolverDocumento`).
- **Consulta RENIEC/SUNAT**: `consultarDocumento('ruc', numero)` ahora también determina esto por el prefijo del RUC devuelto — si empieza en `20`, `nombres` viene `null` y `razonSocial` trae el nombre de la empresa; en cualquier otro RUC, `nombres` trae el nombre completo (SUNAT no separa nombres/apellidos para persona natural con RUC, a diferencia de RENIEC con el DNI) y `razonSocial` es `null`.
- **Body**: `crearClienteSchema`/`actualizarClienteSchema` ahora aceptan `razonSocial` (opcional) y `nombres` pasó de requerido a opcional — la validación de cuál se exige según el documento vive en el service, no en el schema de zod (zod no valida bien reglas cruzadas de "uno u otro según un tercer campo").

### Personal: persona natural o jurídica + dirección (2026-09-09)

- **Regla**: igual que en Clientes, un registro de `personal` cuyo documento es un RUC que empieza en `20` es **persona jurídica** y se identifica por `razonSocial`, sin `nombres`/`apellidoPaterno`/`apellidoMaterno`; cualquier otro documento (DNI, RUC `10`/`15`/`17`, CE, Pasaporte) es **persona natural** y exige `nombres`. Son mutuamente excluyentes: `personal.service.ts` (`resolverIdentidad`) devuelve limpio el grupo de campos que no aplica, tanto al crear como al editar (recalculando sobre el registro ya fusionado, de modo que cambiar el documento de DNI a RUC `20` exige la razón social aunque el resto del formulario no cambie).
- **Diferencia con Clientes**: en `personal` el **documento sigue siendo obligatorio** (tipo y número), a diferencia de `clientes`, donde es opcional. El personal es la base del núcleo de identidad (`empresas → personal → usuarios`) y debe ser identificable.
- **Body**: `crearPersonalSchema` acepta `razonSocial` (opcional) y `nombres` pasó de requerido a opcional; qué campo se exige depende del documento y se valida en el service, no en zod (misma razón que en Clientes: zod no expresa bien reglas cruzadas).
- **Dirección**: `consultarDocumento` ahora devuelve también `direccion` (nuevo campo de `DatosDocumento`). Para RUC se prefiere `direccion_completa` del proveedor (incluye distrito/provincia/departamento) sobre `direccion` (solo la vía); por DNI el proveedor no la entrega en el plan actual y llega `null`. Los valores vacíos o `"-"` se normalizan a `null` (`textoOpcional`), para no guardar texto basura. El formulario de Personal solo sobrescribe la dirección cuando la consulta trae una, respetando lo que el usuario ya escribió.

### Buscador de cliente por documento en Pedidos y Ventas (2026-09-08)

- **Componente frontend** `components/BuscadorCliente.tsx`, usado en el formulario "Nuevo pedido" (`Pedidos.tsx`) y "Nueva venta" (`Ventas.tsx`) en vez de un simple combo de selección. Busca por DNI o RUC: si el número ya es un cliente registrado, lo selecciona directamente; si no, consulta RENIEC/SUNAT y ofrece "Registrar y usar" (crea el cliente automáticamente con los datos de la API); siempre hay un botón "+ Nuevo cliente" para registro manual completo. No agrega ningún endpoint nuevo — la búsqueda de "¿ya existe?" se hace en el cliente contra la lista de clientes ya cargada (`listarClientes`, compartida vía TanStack Query), igual criterio que otras búsquedas derivadas en el frontend (ej. "Ocupación" de Mesas).
- **Componentes compartidos nuevos**: `components/CamposIdentidadCliente.tsx` (nombres/apellidos o razón social, según el documento — usado por `Clientes.tsx` y por el modal de abajo) y `components/ClienteCrearModal.tsx` (el formulario completo de "nuevo cliente", extraído de `Clientes.tsx` para que tanto la página Clientes como `BuscadorCliente` lo reutilicen sin duplicar el formulario).

### Empresa pública para la carta digital (2026-09-09)

- **`GET /api/empresas/publico`**, sin autenticación — devuelve `{ nombre, direccion, telefono, logo }` de la empresa activa más antigua (`empresa.mapper.ts: empresaPublica`), o `data: null` si todavía no hay ninguna empresa configurada; nunca lanza error, la carta debe poder mostrarse igual sin datos de contacto (mismo criterio de degradación que `consultarTipoCambio`/`consultarDocumento`). Expone solo lo que un cliente externo puede ver — **nunca** el RUC ni el email interno.
- El sistema es de un solo local (sección 1 de `CLAUDE.md`), así que no hace falta elegir "cuál" empresa mostrar si hubiera varias; se toma la primera creada que esté activa.
- La ruta se registra antes de `empresaRouter.use(requireAuth)` — mismo patrón que `GET /api/productos/publico`.
- Usado por `PublicLayout.tsx` (nombre/logo en el header, dirección/teléfono en el pie) y `Carta.tsx` (mensaje de WhatsApp con el nombre real del restaurante). Antes de esto, la carta pública mostraba el branding genérico "Restaurant ERP" sin ningún dato real de contacto.

### Archivos subidos (imágenes de producto)

- Middleware: `multer` (disco), configurado en `src/config/uploads.ts`. Solo acepta `image/*` con extensión `.jpg/.jpeg/.png/.webp`, máximo 5 MB; nombre de archivo generado con UUID (nunca se confía en el nombre original).
- Almacenamiento: `apps/backend/uploads/<subcarpeta>/` (fuera de git, ver `.gitignore`). Servido estáticamente en `GET /uploads/...` con `Cross-Origin-Resource-Policy: cross-origin` (necesario porque Helmet por defecto bloquea la carga cross-origin de la imagen desde el frontend en otro puerto).
- Al reemplazar o eliminar un producto, el archivo anterior se borra del disco (`producto.service.ts`) para no acumular huérfanos.
- Errores de Multer (tamaño excedido, tipo no permitido) se traducen a `400` en `error-handler.middleware.ts`, no a `500`.

### Consulta de DNI/RUC (RENIEC/SUNAT)

- Proveedor: **apis.net.pe** (decisión del usuario, 2026-09-07). Un solo token cubre DNI (RENIEC) y RUC (SUNAT).
- Configuración: variable de entorno `APIS_NET_PE_TOKEN` (ver `.env.example`). **Opcional** — si no está configurada, el endpoint responde `503` con un mensaje claro y el resto del sistema sigue funcionando con normalidad; no bloquea el arranque del backend.
- Implementación: `src/modules/catalogos/consulta-documento.service.ts` (movido desde `personal/` el 2026-09-07 cuando Clientes empezó a necesitar la misma búsqueda — vive en `catalogos` por ser una integración SUNAT compartida, no algo específico de Personal), usando `fetch` nativo de Node (sin dependencia nueva), con timeout de 8s. La validación de formato por tipo de documento (`FORMATOS_DOCUMENTO`) vive en `src/modules/catalogos/formato-documento.util.ts`, también compartida entre Personal y Clientes.
- Frontend: botón de búsqueda (icono lupa) junto al campo "N° de documento", componente compartido `components/CampoBusquedaDocumento.tsx` (genérico sobre el tipo de formulario vía generics de react-hook-form), usado en los formularios de crear/editar de Personal y Clientes. Visible solo cuando el tipo de documento elegido es DNI o RUC (los únicos que `apis.net.pe` puede consultar). Autocompleta nombres y apellidos; cada página decide cómo mapear el resultado a sus propios campos (Personal separa apellido paterno/materno, Clientes los concatena en un solo campo `apellidos`).
- **IMPORTANTE (corregido 2026-09-07):** apis.net.pe migró su servicio a la infraestructura de **Decolecta** — el dominio/versión vigentes son `https://api.decolecta.com/v1` (no `api.apis.net.pe/v2`), con un esquema de campos distinto (`document_number/first_name/first_last_name/second_last_name` para DNI; `numero_documento/razon_social` para RUC). El código y el `.env.example` ya apuntan al dominio correcto. Si en el futuro la búsqueda vuelve a fallar con "Token inválido" pese a tener un token vigente, sospechar primero de otro cambio de dominio/contrato del proveedor — probar con `curl` contra la URL configurada antes de asumir que es un bug del código.
